## 📌 0. О чём этот документ и как он соотносится со спецификацией v4.8

Этот документ — **спецификация требований уровня планирования** (ЧТО система должна делать и как проверить, что она это делает). Он **не содержит кода реализации** (КАК — команд nft, jq, скриптов).

Разделение ответственности между документами:

| Документ | Уровень | Критерий завершённости |
| :--- | :--- | :--- |
| **Этот документ (REQ v1.0)** | Намерения, инварианты, критерии приёмки, границы | DoD Блоки A–C (§4) — **без исполнения на железе** |
| `safe-network-system-spec-v4.8.md` | Reference implementation (LLD: код, конфиги, скрипты) | DoD Блок D (§4) — **только зелёный прогон ATP на железе** |

Ключевое архитектурное решение процесса (зафиксировано после ретроспективы циклов v4.2→v4.7→v4.8): **ревью ИИ без исполнения имеет потолок точности**. Код в LLD нельзя довести до нулевого количества находок текстовым ревью — каждый свежий взгляд находит новый класс ошибок (синтаксис, приоритеты хуков, парсинг handle). Поэтому «готовность» определяется не отсутствием замечаний, а **проверяемым покрытием требований тестами + фиксацией границ + stop-rule** (§5).

## 🎯 1. Постановка задачи (Problem Statement)

### 1.1. Базовая потребность владельца

Персональная система безопасного проксирования трафика для обхода блокировок интернет-провайдеров в Российской Федерации. **Pet-проект** для себя и своей семьи; вывод в продакшен и коммерческое распространение **не планируются**.

### 1.2. Целевая архитектура (задана владельцем)

```
[Клиенты LAN/Wi-Fi] → [Роутер: OpenWrt 24.10.5+ на MediaTek Filogic]
                            │
                      sing-box (tun-интерфейс tun0)
                            │
              ┌─────────────┴─────────────┐
        VLESS + Reality            Hysteria2
        (основной, TCP)            (резерв, UDP/QUIC)
                            │
                   [Выходные прокси-узлы]
```

Профили развёртывания:
- **Стационарный домашний шлюз** (Cudy WR3000S или аналог, WAN по Ethernet).
- **Портативный travel-роутер** (Cudy TR3000, WAN по Wi-Fi-repeater или USB-модему телефона, Captive Portal).

### 1.3. Контекст угроз

- Блокировки на уровне DNS, инспекция TLS/SNI (ТСПУ), throttling шифрованного трафика, блокировки по IP.
- Ненадёжная среда исполнения: 256 МБ ОЗУ, NAND-flash с ограниченным ресурсом перезаписи, питание может пропасть в любой момент, SSH-сессия может оборваться посреди конфигурации.
- Оператор системы — один человек (владелец), пользователи — нетехнические члены семьи.

## ✅ 2. Требования

Формат: **ID | Приоритет | Требование | Критерий приёмки**.

Приоритеты:
- **MUST** — инвариант безопасности или базовая функция. Нарушение = система не работает / небезопасна. Блокирует DoD.
- **SHOULD** — важная функция устойчивости/удобства. Деградация допустима и документируется. Не блокирует DoD при явной фиксации.
- **MAY** — опционально, улучшает опыт. Отсутствие не является дефектом.

### 2.1. REQ-S: Инварианты безопасности (неприкосновенны)

| ID | Пр. | Требование | Критерий приёмки |
| :- | :- | :--- | :--- |
| **REQ-S-01** | MUST | **Fail-Closed транзит.** При недоступности туннеля (падение sing-box, исчезновение tun0) весь транзитный трафик клиентов LAN в WAN ДОЛЖЕН блокироваться на уровне ядра. Ни один пакет клиента не уходит напрямую провайдеру. | ATP T5: при остановленном sing-box `curl` с клиента немедленно отвергается; после старта — HTTP 200. |
| **REQ-S-02** | MUST | **Fail-Closed для трафика самого роутера.** Router-originated трафик (opkg, обновления, алерты) при отсутствии tun0 ДОЛЖЕН блокироваться, кроме явного whitelist (NTP, DHCP, bootstrap-DoH, окно Captive Portal). | ATP T33, T36. |
| **REQ-S-03** | MUST | **Нет утечек DNS.** Все DNS-запросы клиентов перехватываются и резолвятся только внутри системы (sing-box); сторонние DNS, браузерный DoH и DoT из LAN блокируются. | ATP T8 (`dnsleaktest.com` показывает только доверенные резолверы). |
| **REQ-S-04** | MUST | **Нет утечек IPv6.** Транзитный и router-originated IPv6 (кроме loopback) блокируется, если туннель его не поддерживает. | ATP T42 (транзит), проверка правила IPv6-reject в output guard (output). |
| **REQ-S-05** | MUST | **Защита от WebRTC/QUIC-обхода.** WebRTC-утечки и прямой UDP/443 из LAN блокируются (Hysteria2 роутера при этом работает). | ATP T8, T9. |
| **REQ-S-06** | MUST | **Откатываемость изменений.** Любое изменение firewall или config.json применяется только с автоматическим таймером отката (Lock-Rollback), переживающим обрыв SSH-сессии. Откат НЕ ДОЛЖЕН требовать физического доступа к устройству. | ATP T23: обрыв SSH во время применения → автовосстановление через 300 с, запись в логе. |
| **REQ-S-07** | MUST | **Защита секретов при изъятии устройства.** История конфигураций с секретами (UUID, ключи Reality, токен API) НЕ ДОЛЖНА персистентно храниться на NAND. API управления требует аутентификации. | ATP T34 (git в tmpfs), T10 (HTTP 401 без токена). |
| **REQ-S-08** | MUST | **Трафик клиентов «direct» не покидает fail-closed контур.** Выборочная маршрутизация клиентов (напр., SmartTV напрямую) реализуется внутри sing-box и остаётся fail-closed при падении демона. | ATP T38, T40: direct-клиент показывает IP провайдера; при остановленном sing-box — отказ соединения. |

### 2.2. REQ-F: Функциональные требования

| ID | Пр. | Требование | Критерий приёмки |
| :- | :- | :--- | :--- |
| **REQ-F-01** | MUST | **Двухтранспортность.** Поддерживаются VLESS+Reality (основной) и Hysteria2 (резерв); оба присутствуют в пуле автовыбора. | ATP T41, T9. |
| **REQ-F-02** | MUST | **Раздельная маршрутизация РФ/мир.** Трафик к российским ресурсам идёт напрямую (Direct), к заблокированным — через туннель, без участия пользователя. | ATP T7 (`2ip.ru` → IP РФ, `icanhazip.com` → IP прокси). |
| **REQ-F-03** | MUST | **Конвейер подписок.** Конфиг генерируется из подписки компилятором (`sub2sing.py`), валидируется (jq + sing-box check + fw4 check) и атомарно активируется с Lock-Rollback. Пустой пул узлов НЕ ДОЛЖЕН порождать фатальный конфиг. | ATP T24, T2; валидация `_build_outbounds` (ретроспектива R-V8-7). |
| **REQ-F-04** | SHOULD | **Резервная подписка.** При полном отказе пула узлов система пытается получить резервную подписку, не входя в deadlock (fetch не зависит от мёртвого прокси-пула). | ATP T29; архитектурная проверка mark-байпаса 0xfe (R-V8-5). |
| **REQ-F-05** | SHOULD | **Multi-WAN (travel-профиль).** Автопереключение Wi-Fi ↔ USB-модем с выбором LTS-пула узлов на мобильном канале. | ATP T11. |
| **REQ-F-06** | SHOULD | **Captive Portal.** Трёхступенчатая развязка гостевых порталов с автоматическим закрытием окна (≤180 с) и возвратом в fail-closed состояние. | ATP T36, T18. |
| **REQ-F-07** | SHOULD | **Выборочная маршрутизация клиентов LAN.** Отдельные устройства (по IP) назначаются в direct / стандартный пул / LTS-пул через декларативный конфиг с атомарным применением и откатом. | ATP T38, T40. |
| **REQ-F-08** | SHOULD | **Ручной выбор узла.** Оператор может принудительно выбрать узел/группу через веб-панель или API. | ATP T9 (MANUAL-SELECT). |
| **REQ-F-09** | MUST | **Холодный старт без DNS и туннеля.** NTP-синхронизация по IP и bootstrap-резолвинг ДО поднятия туннеля (Reality требует верного времени). | ATP T4, T37. |
| **REQ-F-10** | SHOULD | **Двухпуловая логика узлов.** Standard-пул (топ-N по задержке) и LTS-пул (стабильные для мобильного канала) формируются автоматически из подписки. | ATP T41 (конфиг), T11 (поведение). |

## 🏁 4. Definition of Done

### 4.1. DoD для ЭТОГО документа (Requirements Specification v1.0)

Документ считается **финальным**, когда выполнены все пункты:

**Блок A. Полнота покрытия**
- [x] **A1.** Каждое требование имеет уникальный ID, приоритет (MUST/SHOULD/MAY) и формулировку «ДОЛЖНО/НЕ ДОЛЖНО».
- [x] **A2.** Каждое требование трассируется ≥1 в проверяемый критерий приёмки (ATP-тест или архитектурную проверку). Матрица §3 не содержит строк с пустой колонкой тестов.
- [x] **A3.** Все инварианты безопасности (REQ-S-01…08) сформулированы проверяемо, включая отрицательные сценарии («при падении X трафик блокируется»).

**Блок B. Непротиворечивость и границы**
- [x] **B1.** Требования не противоречат друг другу и модели угроз (§1.3, REQ-O-04).
- [x] **B2.** Границы системы зафиксированы: что вне scope (REQ-O-04), что субъективно и не блокирует приёмку (REQ-O-05).
- [x] **B3.** Юридическая рамка зафиксирована (REQ-O-01).

**Блок C. Приоритизация под pet-проект**
- [x] **C1.** Требования разделены на MUST (инварианты безопасности — недопустимы к нарушению никогда) и SHOULD/MAY (деградация допустима и задокументирована). Владелец осознанно принимает, что SHOULD-сбой (напр., час без резервной подписки) — не дефект готовности, а эксплуатационное событие.

### 4.2. DoD для реализации (LLD v4.8 как reference implementation)

Реализация считается **готовой**, когда:

- [ ] **D1.** Все MUST-требования подтверждены зелёным прогоном соответствующих ATP-тестов **на целевом железе** (минимум один профиль: стационарный ИЛИ travel).
- [ ] **D2.** Все инварианты REQ-S-01…08 подтверждены **отрицательными тестами** (T5, T23, T33, T40-часть-в, T42) — не «код выглядит правильно», а наблюдаемое поведение.
- [ ] **D3.** Каждый SHOULD-сбой, обнаруженный при прогоне, либо устранён, либо вписан в Known Limitations с явным согласием владельца.
- [ ] **D4.** DoD документа-требований (4.1) подписан и заморожен.

**До выполнения D1–D2 LLD v4.8 имеет статус «кандидат реализации», а не «рабочая система»** — независимо от количества пройденных раундов текстового ревью.

### 4.3. Stop-rule и управление изменениями

- **E1. Заморозка.** После подписания 4.1 новые находки к тексту требований НЕ переоткрывают v1.0 — они идут в errata-лог следующей минорной версии (v1.1).
- **E2. Классификация находок к LLD.** Только **Critical/High** (нарушение инварианта REQ-S-*, потеря данных, нерабочий fail-closed) открывает новую минорную ревизию LLD. **Medium/Low** (стиль, микрооптимизации, гипотетические race) — в backlog, без блокировки.
- **E3. Лимит раундов ревью.** Максимум **3 раунда** внешнего текстового ревью на версию LLD (израсходовано: v4.2→v4.7→v4.8). Дальше арбитром истины является **исполнение ATP на железе** (Блок D), а не следующий ИИ-эксперт.
- **E4. Критерий «проект завершён».** Проект считается завершённым, когда: (а) REQ v1.0 подписан по 4.1; (б) LLD прогнан по D1–D3 на обоих профилях; (в) результаты F1–F4 зафиксированы в эксплуатационном журнале. После этого проект переходит в режим **эксплуатации**, а любые изменения — обычный change management (новое требование → v1.1; баг → патч LLD).

## 🧭 5. Ретроспектива процесса (почему DoD устроен именно так)

Цикл v4.2→v4.7→v4.8 показал: текстовое ревью находит 7–8 валидных багов за раунд **неограниченное число раундов**, потому что LLD содержит ~2600 строк неверифицированного кода, а статическое чтение не может доказать отсутствие дефектов. Выявленные классы багов (синтаксис nft, приоритеты хуков, парсинг handle, пустые массивы в jq) неисчерпаемы при ревью и исчерпаемы при исполнении.

Поэтому данный DoD:
1. Отделяет **завершимый уровень** (требования — конечный проверяемый список) от **условно-завершимого** (код — верифицируется только тестами на железе).
2. Заменяет нефальсифицируемый критерий «ИИ не нашёл багов» на фальсифицируемый «все MUST-тесты зелёные, инварианты проверены отрицательными сценариями».
3. Вводит stop-rule (E3), легализующий конец цикла ревью.
4. Калибрует строгость под pet-проект (Блок C1): инварианты безопасности — бескомпромиссны, комфорт — по остаточному принципу.
